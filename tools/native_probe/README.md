# ACU native probe

This is a Windows x64 in-process observation framework and a separate executable
launcher. The original ACU executable is never patched, renamed or replaced.
No game function addresses or structure layouts are enabled automatically.
Generic facilities apply to animation, skeletons, movement, climbing/traversal,
collision/raycast, physics, input, camera, AI, world/streaming and rendering;
their meanings still require independent target and layout recovery.

## Build and run

From the project directory, with existing MSVC 2022 x64 BuildTools:

```powershell
./tools/native_probe/build.ps1
./local/native-probe/ACU-Probe.exe
```

The convenient zero-argument executable reads adjacent ignored `launch.ini`
(`[launch] exe=...`) generated from `python tools/acu.py paths` and loads adjacent
`acu_probe.dll`. All outputs stay under ignored `local/native-probe/`.
Advanced modes:

```powershell
./local/native-probe/acu_probe_launcher.exe --launch "<game-directory>/ACU.exe" --dll "$PWD/local/native-probe/acu_probe.dll"
./local/native-probe/acu_probe_launcher.exe --attach 1234 --dll "$PWD/local/native-probe/acu_probe.dll"
python tools/native_probe/client.py 1234 command STATUS
./tools/native_probe/command.ps1 -ProcessId 1234 -Command MODULES
```

The launcher accepts only original executable SHA-256
`748abdc6456397fe7d8080f975f2a5ed3123bce548e7bf1c68b23f47e8b27e40`
or the exact synthetic fixture hash generated by its own build. The original
must initialize its primary-thread loader normally before DLL injection. The
fixture validates the fully suspended-primary injection path. A failed fixture
injection terminates only that newly spawned suspended fixture; a game that
already started remains running on injection failure. Attach never terminates
its target. Remote system export addresses use enumerated remote module bases;
initial fixture loader bootstrap verifies ntdll header/code bytes before use.

`injected:true` reports successful LoadLibrary completion, not a healthy game
session. The launcher separately observes original-game startup for3seconds,
checks a bounded STATUS round trip, and emits `process_running`,
`process_exit_code`, `probe_status_ready` and `startup_observation_ms`. Exit6
means injection failure,7 means the process exited,8 means STATUS unavailable.
This observation covers that interval only, not subsequent gameplay stability.
On this machine direct original launch, without instrumentation, was
observed to exit code42 after approximately3seconds. Startup injection succeeded
once but that process also exited before a sustained STATUS round trip. These
are platform/game startup availability limits; original-game telemetry remains
unvalidated until a normal game session is available. Read-only installed-game
registry evidence identifies Ubisoft Launcher install720. A user/platform
launched game can be attached by explicit PID. Do not claim fixture results as
original-game parity.

## Transport and limits

The pipe `\\.\pipe\acu-probe-<PID>` rejects remote clients and uses the default
Windows process security descriptor. One local client/command at a time. Send
one ASCII command in one write (max65535bytes); receive one JSON line; send
`ACK` before closing. The bundled clients implement this acknowledgement so a
disconnect cannot discard unread response bytes. Pipe transfers timeout after
30seconds. Access is intended for the local collaborating user, not a network
service or privilege boundary.

| Command | Effect and bound |
| --- | --- |
| `STATUS` | PID, ASLR image base, QPC frequency, hooks/hits/drops/conflicts, capabilities |
| `MODULES` | Names, local paths, ASLR bases and sizes |
| `THREADS` | Current process thread IDs |
| `REGIONS [hex-VA]` | Up to256 VirtualQuery regions, protections/state/type and pagination address |
| `READ hex-VA decimal-length` | Exact bounded read,1..65536bytes; inaccessible/partial reads fail |
| `HOOK slot hex-RVA expected-lowercase-hex label [every register-index signed-offset bytes]` | Verified executable-site probe, slots0..3, expected bytes1..32; sample size0..256 |
| `HOOKVA slot hex-VA expected-lowercase-hex label [every register-index signed-offset bytes category]` | Same guards for an absolute executable address in any loaded module |
| `GATHER slot reg-index signed-disp deref(0/1) data-offset count-offset max-elements bytes` | On each sampled hit of that slot's hook, follow a pointer array inside the handler: base = register+disp (optionally dereferenced once), data = `*(base+data-offset)`, count = u16 at `base+count-offset`, then copy `bytes` (1..768) from each of up to 16 elements. A new `HOOK` in the slot clears it |
| `UNHOOK slot` | Restore affected debug-register slot to its original state |
| `EVENTS [count]` | Drain bounded ring; return newest up to256events, discard omitted older events |
| `WATCH label hex-VA decimal-length` | Up to32 absolute-memory watches, each1..4096bytes |
| `WATCHES` | Latest bytes and cumulative samples/changes/read failures |
| `UNWATCH label` | Remove watch |
| `SHUTDOWN` | Restore debug registers, stop worker and pipe; leave inert DLL/VEH resident |

`HOOK` RVAs are relative to the **main executable**. An RVA, executable-page
protection and a byte match are necessary guards, not proof of function identity.
Call sites must first be mapped to the installed/live image; corpus export VAs
cannot be copied as verified offsets. Expected-byte matching requires exact
lowercase hexadecimal without `0x` or whitespace. Labels have no whitespace.
An optional final category token follows the four sampling arguments. Every
event preserves its own immutable label/category/revision/address across slot
rotations. The handler requires both a registered address and its owned DR6 slot
bit; unrelated single-step exceptions continue through the exception chain.
Function prologues are optional: a separately verified post-call instruction
site can capture RAX/XMM0 and output buffers as another labelled probe. That
requires recovered ABI/native semantics. There is no speculative automatic
return breakpoint or unwind engine.

Register array order is RCX,RDX,R8,R9,RAX,RBX,RSI,RDI,RBP,RSP,R10,R11,R12,R13,R14,R15.
Each event records QPC time, sequence, thread, slot, RIP, all16GP registers,
XMM0..5 raw96bytes, up to64bytes at RSP (caller/arguments), and optional memory
at selected register+signed offset. Snapshot reads occur inside the handler;
pointer failures yield empty/partial data, never fabricated structures. They add
latency and may alter game scheduling. Pointer snapshots and module snapshots
are not coherent cross-thread captures. Stack bytes are not an unwound callstack.

Hardware execution breakpoints preserve original instructions and ABI, but
only **four sites concurrently per thread** are available. Threads with
pre-existing occupied slots are skipped for those slots and counted as
conflicts. A debugger attached at HOOK time rejects activation. Do not attach a
debugger or another hardware-probe owner while these probes are active. Existing
threads are briefly suspended to set/restore debug registers. Their original
registers are saved, thread creation stamps distinguish recycled IDs, and new
threads are refreshed at roughly50ms; short-lived threads can escape coverage.
Known threads are not repeatedly suspended while hook revision is unchanged.
The probe worker is excluded. Exception handlers are not an invisible observer:
measure overhead before using a high-frequency site.

The256event ring drops on contention and overwrites oldest records when full;
STATUS reports combined drops/overwrites. Event sequence counts all captured
hits before sampling. `every=N` samples each Nth hit independently per slot.
Watch polling is approximately20Hz while idle and can pause while a client is
connected; `WATCHES` samples explicitly. Watches are **not frame-synchronized
bone capture**. Entry/post-call correlation is by thread/site/time and can be
incomplete because of nested calls, lost events, rotation, or thread coverage.
Owned breakpoint sites are retained in a bounded tombstone table so pending
single-step exceptions remain handled after UNHOOK. SHUTDOWN deliberately leaves
the inert DLL and this handler resident until process exit; unloading executable
handler code during a pending exception would risk a use-after-unload.

## Whole-image recovery and sessions

For controller-first menu entry, bounded XInput sweeps and the category checkbox
launcher, see
[`docs/CONTROLLER_AUTOPLAY.md`](../../docs/CONTROLLER_AUTOPLAY.md). The runner
can capture read-only memory checkpoints and correlate a concurrent verified
native probe session with decompile-name candidates.

An opt-in native startup dump can capture a short-lived original before orderly
exit without pipe round-trip overhead. Set `$env:ACU_PROBE_STARTUP_DUMP='1'`
and optionally `$env:ACU_PROBE_STARTUP_DUMP_DELAY_MS='500'` (0..2000), then run
the launcher. The worker writes unique `startup-PID-TICK.mapped.bin` and `.json`
adjacent to the DLL, capped at512MiB main image; manifest records module base,
regions/protections/read holes, disk/mapped SHA256, QPC times and completeness.
It does not enable any hooks or decode structures. This sequential sample may
still contain packed or partially unpacked code; inspect contents before using
it as native evidence. Remove these environment variables after capture.

```powershell
python tools/native_probe/client.py 1234 dump local/native-probe/live-session
python tools/native_image.py local/native-probe/live-session/main-image.mapped.bin local/native-probe/live-inventory --mapped --live-base 0xBASE
python tools/decompile_xref.py local/native-probe/live-inventory/functions.jsonl local/native-probe/live-inventory/summary.json "ACU - Decompiled" local/native-probe/live-xref
python tools/decompile_xref.py local/native-probe/live-inventory/functions.jsonl local/native-probe/live-inventory/summary.json "ACU - Decompiled" local/native-probe/live-xref --session local/native-probe/session.jsonl
python tools/native_probe/client.py 1234 scan 0000000012340000 65536 "48 8b ?? 24"
python tools/native_probe/client.py 1234 dump local/native-probe/all-memory --all-regions --max-bytes 4294967296
python tools/native_probe/client.py 1234 session local/my-verified-profile.json local/native-probe/session.jsonl --seconds 60 --max-bytes 16777216
```

Main-image output preserves mapped RVA layout, zero-filled holes and a manifest
of region protection/state, every unreadable range, module identity, source
disk executable SHA-256 and captured live-file SHA-256. Reads are64KiB with4KiB
fallback; guard/inaccessible/noncommitted pages are skipped. It is a sequential
capture while the game runs, not an atomic snapshot. `--all-regions` creates
separate files with absolute region bases and explicit4GiB default budget;
larger committed-memory scopes must be requested explicitly. Dumps contain game
bytes and possibly sensitive process data: keep them in ignored machine-local
storage. Scan is bounded64MiB/256-byte pattern/256matches and reports holes.

`profiles.example.json` provides subsystem categories but intentionally has no
unverified offsets. Add `probes` objects with `label`, hex `rva`, `expected_hex`,
optional `every`, `register_index`, `offset`, `bytes`, `category` and `module`.
`module` selects one loaded module name, bounds its RVA, and uses HOOKVA;
the session header records module paths/bases/disk hashes. Session profiles rotate
groups of up to4 probes, emit group metadata/time/status and bounded JSONL,
and remove active probes on exit. Categories are organizational metadata,
not implemented semantic decoders. Rotated groups observe different time
windows: whole-profile breadth does not mean whole-engine simultaneous coverage.
An optional `redirect` object can set `slot`, `from_index`, `to_index`,
`return_module` and hex `return_rva`; the exact conditional RCX redirect is
applied before the session emits `armed`. It requires a redirect-capable probe
DLL. The controller replay waits for that flushed `armed` record before sending
input. A regular probe DLL rejects the command, and no replay should start on
that failed session.
When `controller_autoplay.py` receives `--expected-user-index`, it skips the
moving stick calibration pulse and verifies the first non-neutral XInput
readback against the requested report. Without that option it discovers the
slot with the pulse and confirms release before replay.
Use separately labelled entry and verified post-call sites for traversal tests
and raycast arguments/results when those native layouts are recovered.

### Several ACU instances at once (one per session)

The safety rules hold for every instance, unchanged:

- **Close a game only with `python tools/native_probe/capture_run.py --close <pid>`**, and only
  your own PID. Never `taskkill` by image name: that would close every session's game.
- **Never hot-swap or remove the shim on a running game** (`focus.py remove`, or `remove` then
  `install`); both took over the user's mouse and keyboard on 2026-11-14.
- **Always launch with an explicit `--fps-cap` of 300 or lower** (`30..240` is plenty), never
  `--fps-cap 0`. Several capped games are fine; one uncapped game stalled the PC. Cap each
  instance so the total load stays reasonable.

What `capture_run.py` does so that sessions do not grab each other's game:

- `launch()` records the running ACU PIDs, starts `uplay://launch/720/0` and waits for an engine
  window (`ScimitarEngineWindowClass`) whose PID is new. The shim, probe, watchdog and
  `shutdown()` key on that PID only. If no new instance appears within 120 s it fails with
  "Ubisoft Connect did not start a second instance" and touches no existing game. If two new
  PIDs appear at once (a launch outside `capture_run`), it refuses both.
- Launches are serialised by `local/native-probe/launch.lock` (held from the PID snapshot until the
  new window appears), so two sessions launching together each get their own game. Shim installs
  are serialised by `focus-install.lock`: `focus.install` writes the one shared `acu_focus.ini`
  (fps cap, input block, return window), which the shim reads while it loads. Lock files are
  created with `O_CREAT|O_EXCL` and taken over when stale; delete one by hand only when no
  capture runs.
- The window the shim hands the foreground back to is the user's current foreground window,
  unless that window belongs to an ACU.exe (another session's game); then none (0).
- `--attach <pid>` is unchanged; pass your own game's PID.

**Ubisoft Connect starts only one game** (tested 2026-11-15): with one ACU running,
`uplay://launch/720/0` started no second one within 120 s. Use `--direct` for more than one game.

#### Direct launch (`--direct`) and `multi_launch.py`

```powershell
python tools/native_probe/multi_launch.py 2                         # two games, title screen
python tools/native_probe/multi_launch.py 2 --until world --save-pin capture-start-1
python tools/native_probe/capture_run.py local/native-probe/runs/<name> --direct --until world
python tools/native_probe/instance_guard.py list                    # PIDs still holding the guard
```

- `--direct` starts `ACU.exe` itself from the game folder (`ACU_GAME_DIR` or
  `local/project.json`). It does not go through `uplay://`. The spawned PID is the game. This works
  with the `uplay_r1_loader64.dll` installed on 2026-11-15 (not Ubisoft's, see ACU-RE-0085); it
  has not been tried with the signed loader.
- Loaders: `python tools/loader_swap.py use custom` before running several games, and
  `use original` for single-game runs (Ubisoft-signed loader, stock state). Swaps are renames between
  `uplay_r1_loader64.dll`, `.dll.bak` (original) and `.dll.custom` (custom), checked by SHA-256 and
  refused while any ACU.exe runs. `.3dm` is a spare copy of the original and is never touched. The log is
  `local/game-backups/loader-swap/log.jsonl`. `--direct` and `multi_launch.py` refuse unless the custom
  loader is active. `status` shows which loader is in use.
- ACU's single-instance check: a second `ACU.exe` exits with code 0 before opening a window while a
  running game holds the named semaphore `scimitar_semaphore` (count 1 of 1, held by nobody).
  Inside the launch lock, once the new game's window is up, `capture_run` closes that game's own
  handle (`instance_guard.release`, `DuplicateHandle` with `DUPLICATE_CLOSE_SOURCE`). This is
  recorded as the `guard` stage. The next launch then starts. The uplay path does the same for its
  game.
- A game that still holds the guard (launched some other way) blocks `--direct`. `capture_run`
  then stops and names the PID; it never closes another session's handle. If that game is yours,
  run `instance_guard.py release <pid>`.
- `multi_launch.py N` (1..4) runs N `capture_run.py --direct --until title|world` runs, staggered
  by 2 s; the launch lock serialises them. Each run gets its own shim, probe and save-pin lease
  holder. Output: `local/native-probe/runs/multi-<stamp>-<i>/` plus a `multi-<stamp>.json`
  summary with the close and `save_pin.py release` commands for each game.
- `--until title` stops after attaching (shim and probe in, game at the title screen).
- Load. `multi_launch.py` keeps a second game light by default:
  - **`--fps-caps 60,30`:** the first game (the one you watch) runs at 60, every further game at 30.
    From 15 to 30 fps ACU's physics takes one 1/30 s step per frame (ACU-RE-0051), so 30 is the
    lowest cap that keeps the physics stepping the same way.
  - **`--cpu-split auto`:** every further game gets 2 logical processors from the top at below-normal
    priority; the first keeps the rest at normal (6 threads: 0-3 / 4-5).
  - Use `none` to turn the split off, or give one core list per game, e.g. `0-7/8-11`.
  - `capture_run.py --cpu-cores 4,5 --priority below_normal` sets the same for one run. A `--direct`
    game starts suspended, gets its cores and priority, and is then resumed, so the engine sizes its
    workers to its own cores. If either cannot be set, the never-run process is terminated.
  - `python tools/native_probe/game_load.py --seconds 30` measures every running game: CPU share,
    working set, shim fps and core mask.
- Evidence and limits: [ACU-RE-0086](../../docs/findings/ACU-RE-0086-multi-instance-direct-launch.md).
  The game code that creates and checks the semaphore is not located. The game keeps the closed
  handle value. Closing it has caused no visible fault so far.

Saves (`--save-pin`): all instances share the one `savegames/<user>/720` folder, so a pin cannot
be swapped per game. Runs share a lease instead, `local/game-backups/save-pins/_lease.json`
(`{pin, snapshot, holders:[{holder, pid, owner_pid, since_unix}]}`, guarded by `_lease.lock`):

- the first run (no lease, no ACU running) swaps the pin in and opens the lease;
- a run on the same pin joins without copying; it loads the slot as it is now, which another
  running game may have autosaved over, so `capture.json` records `live_matches_pin`;
- a run on a different pin is refused, and so is `--save-pin` while any ACU runs without a lease
  ("saves cannot be swapped under it; run without --save-pin");
- each run's holder is its run directory, tied to its game PID after launch; holders whose game
  (or, before launch, whose `capture_run` process) is gone are pruned;
- the last holder to release puts the saves back only when no ACU.exe runs at all; otherwise
  the lease waits for `python tools/save_pin.py settle`. A lease left with no live holders and no
  game is put back by the next `acquire`, which then starts over.
- `--until world` keeps the lease for as long as the game runs and prints the release command;
  after `capture_run.py --close <pid>` run `python tools/save_pin.py release "<run dir>"`.
- `python tools/save_pin.py lease` shows the lease and which holders are alive; `pin`, `use` and
  `putback` still refuse while any ACU runs.

Coordination: the game-process lock (GitHub issue #30, ACQUIRE/RELEASE comments) becomes
per-PID with several instances. ACQUIRE and RELEASE name the PID you launched (from the
`launch` stage in `capture.json`); never act on a PID another session acquired.

## Background runs: focus shim and in-process controller

For a whole capture in one command (launch, load the save, scenario, decode, close) use
`capture_run.py`; see `docs/CONTROLLER_AUTOPLAY.md` "One-command capture".

`acu_focus.dll` (source `focus.cpp`) keeps ACU running and controllable while another window
has focus, so captures need no attention from the user:

```powershell
python tools/native_probe/focus.py install <pid>    # copy + inject; waits for focus-<pid>.json
python tools/native_probe/focus.py status <pid>
python tools/native_probe/focus.py remove <pid>     # restores everything listed below
python tools/native_probe/focus.py activate <pid>   # posts activation messages so Start/Back menus open
```

- **Closing the game: only `python tools/native_probe/capture_run.py --close <pid>`.** The shim stays
  installed while ACU closes (graceful for 15 s, then `taskkill /F`, `ClipCursor(NULL)` from outside
  throughout). Never `focus.py remove` a game that is about to close: on 2026-11-14 a shutdown that
  hung after the shim was removed took over the user's mouse and keyboard and stalled their PC.
  Never hot-swap the shim (`remove` then `install`) on a running game either: a swap loop to
  change the fps cap grabbed the user's mouse the same day. Choose the build and cap at launch.
- Data-write watches (probe build with `HOOKDATA`, 2026-11-14; previous build kept as
  `local/native-probe/acu_probe_pre-hookdata.dll`, copy it back to `acu_probe.dll` to restore):
  `HOOKDATA slot hex_address length(1,2,4,8; aligned) label [every offset bytes category]`.
  The trap fires after the writing instruction (`rip` = next instruction; for a leaf writer
  `return_address` is its caller). The snapshot is taken at `address + offset`, and data slots
  keep 512 stack bytes. `position_writers.py PID OUT` watches the player transform
  (ACU-RE-0056). `root_motion_link.py PID OUT [--stick X Y] [--body]` watches the skeleton's
  root delta, the BipedComponent velocity request and, with `--body`, the position target and
  body translation (ACU-RE-0057). `root_delta_capture.py PID OUT` records the root delta per
  frame with the playing leaves, for `tools/root_delta_compare.py` (ACU-RE-0058). Never watch a
  job-worker stack slot (~49k traps/s).
- **Stale debug registers (fixed 2026-11-14, build `d7b69cca…`):** `SetThreadContext` on a thread
  inside the trap handler is undone when the handler returns its saved context, so one thread can
  keep an old watch after `UNHOOK`. That crashed ACU once (unhandled single step in d3d11). The
  handler now re-syncs DR0-3/DR7 on every trap and claims traps on any address the probe armed;
  `STATUS` shows `stray_traps`. Previous build: `local/native-probe/acu_probe_pre-drsync.dll`
  (copy back to `acu_probe.dll` to restore). Never put an execute hook on hot routines such as `0x1420F6F70` (~11k calls/s);
  arming it stalled the client.
- **Always launch with an explicit frame cap** (`--fps-cap 30..240`; nothing above 300 is needed).
  Never `--fps-cap 0`: an uncapped run on 2026-11-14 stalled the user's whole PC.
- After a teleport, menus and the map ignore Back/Start/M until Arno moves; walk 1 s first. On
  the map the cursor sits at the screen centre and short WASD taps (0.045-0.065 s through
  `InProcessKeys`) step it between nearby icons; F1/F3 cycle filters (ACU-RE-0054).
- Travel guard (shim build t8+, the default `acu_focus.dll` since 2026-11-14; the previous default
  t4 is kept as `acu_focus_t4.dll`, copy it back to restore): teleport and flag requests answer
  `-5` while the travel manager `[0x145219860]+644` is not 0, and `-6` when the entity is not the
  current World's player (stale pointer after a world change or reload). World-load requests
  (modes 3/4) answer `-5` while a travel runs. `teleport.ready()` / `wait_ready()` check the same
  from Python and raise `teleport.NotReady` without sending anything.
- `teleport.py <pid> keep-safe`: re-arms Invisible + God Mode whenever a new player entity appears
  (each world arrival, death or reload makes a new one; ACU-RE-0049 obs. 15).
- Keyboard (shim build t7+): `focus.InProcessKeys(pid)` writes `Localcu-keys-<pid>`
  (`<III256B`: magic `ACUK`, enabled, sequence, one held flag per DirectInput scancode). Held keys
  are ORed into the game's DirectInput keyboard `GetDeviceState` reads, and each change is queued
  as a buffered `GetDeviceData` event. Use it for menu actions that only show keyboard prompts
  (map fast travel: F, then Enter). `tap("F")`, `hold(["LSHIFT", "W"])`, names in `focus.DIK`.

- Window: the game's top-level window is subclassed and deactivation messages are dropped;
  `GetForegroundWindow`/`GetActiveWindow`/`GetFocus` return the game window inside ACU, and
  `XInputEnable(FALSE)` is ignored. Without this, loading stalls when the game is unfocused.
- The user's desktop never reaches the game: while the game is *really* in the background
  (original foreground query), `GetCursorPos` returns the last focused position and DirectInput
  `GetDeviceState`/`GetDeviceData` report no input. Focused, everything passes through.
- In-process controller: when a runner writes into `Local\acu-pad-<pid>`, XInput user index 0
  reports a connected pad with that state, and the window receives `WM_DEVICECHANGE` so the
  game enumerates it. No device or driver is involved and no other process sees the pad.

- User input block: `focus.py install <pid> --block-user-input` (the runner's default) keeps
  the user's mouse and keyboard out even while ACU really has the foreground, drops its
  `ClipCursor`/`SetCursorPos`/`ShowCursor(FALSE)` (reported as -1, since ACU hides in a loop
  until the count is negative) and hands the foreground back to `return_focus` during the
  first 90 s.
- Player state: `player_state.py <pid>` reads the player entity and transform (ACU-RE-0044);
  `navigate.py <pid> goto X Y` / `face DEG` drive Arno there in closed loop.
- Teleport: `teleport.py <pid> to X Y Z` writes the player entity matrix and calls the Human's
  behaviour reset (`0x14131A530`) on the game window's thread through the shim's
  `Local\acu-teleport-<pid>` section (ACU-RE-0046). Heading is not kept (the reset restores it);
  pick Z on known ground. `vault_scan.py` uses it to free-run outwards from many ground points
  and ranks the spots where vault clips (`SkipOver`/`SlideOver`/`JumpOn*`) start.
  `teleport.py <pid> invisible on` / `godmode on` set the debug menu's flags (enemies ignore
  Arno; no death). A teleport that ends more than 1.5 m below its target (ground not streamed)
  is retried with longer waits.
- World inventory: `world_entities.py <pid> out.json` lists loaded entities (World pointer at
  +0x60, rigid matrix at +0x20, name via [E+0x130]+0x10). `hop_scan.py` teleports across a
  whole region and maps it; `tools/prop_moves.py` labels prop types from probe runs.
- Frame limiter: `focus.py install <pid> --fps-cap N` writes `acu_focus.ini`; the shim paces
  `IDXGISwapChain::Present` (vtable slot 8, found through a throwaway swap chain) to N per
  second and reports the measured rate in `frame.fps`.
- The game window is found by its engine class, `ScimitarEngineWindowClass`, even when it is
  minimised. A minimised ACU stops presenting; restore it without activation
  (`ShowWindow(hwnd, SW_SHOWNOACTIVATE)`) or keep it on another virtual desktop.

Patches are 5-byte `jmp rel32` to a nearby trampoline (some user32 exports are 6-byte
stubs); call-through originals are only built for prologues whose first instruction is
exactly 5 position-independent bytes. Removal restores the saved bytes, the two DirectInput
vtable slots and the window procedure; the DLL stays resident as an inert module. The shim
writes `focus-<pid>.json` beside its DLL copy. Never edits game code, files or saves.

## Verification and restoration

### Read-only exact signature discovery

Hit-capped scans now record `partial_chunk` and `resume_address`; `next_address`
uses that resume point. A single pattern resumes at the last hit plus one byte.
Multiple patterns resume at the chunk start and may duplicate prior hits;
deduplicate and choose an adequate hit budget. Cross-chunk overlap at a resume
boundary still needs broader controls.

### Runtime image analysis view

python -m tools.native_probe.runtime_analysis_view <pid> local/runtime-view --expected-sha256 <exe-sha256>

### Signature scanner usage

`scan_memory_signature.py` uses external `VirtualQueryEx` and
`ReadProcessMemory`; it does not need an injected probe. It verifies the PID's
executable path and required SHA-256 before scanning. Supply reference bytes
through one or more `--pattern-file` arguments and explicit address bounds:

```powershell
python tools/native_probe/scan_memory_signature.py <pid> local/signature-scan.json --pattern-file local/reference.bin --expected-sha256 <exe-sha256> --start 0x100000000 --end 0x180000000
```

The output records exact hits, reference hashes, readable-byte coverage, failed
reads, and the stopping address/reason. Defaults bound successful reads to
4 GiB, elapsed time to 45 seconds, and hits to 256; `--max-bytes`,
`--max-seconds`, and `--max-hits` are explicit overrides. Existing outputs are
refused. Patterns are limited to 4,096 bytes each and 256 files. Reads skip guard
and inaccessible regions and preserve protection settings. Pattern overlap is
retained between chunks within a region; patterns spanning separate regions or
failed reads may be missed. Buffers race application writers. A byte match or
pointer match alone does not identify a player or establish object ownership.
See [ACU-RE-0024](../../docs/findings/ACU-RE-0024-pose-signature-rediscovery.md)
for the positive/negative controls and current ACU pose discovery evidence.
